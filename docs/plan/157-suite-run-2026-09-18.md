## The single highest-leverage defect, and it is in the fake

`venue_http.py:164` serves `/price/ohlc` as `{"data": [ {timestamp, open, high, low, close,
volume}, ... ]}`. The real venue serves TradingView-style parallel arrays — measured directly
this afternoon, the keys are exactly `c, h, l, nextTime, o, t, v` — and every reader in the tree
parses it that way (`provider.py:563`, `broker.py:1180`, `l0_order_semantics.py:191`).

Two consequences, one loud and one silent:

- **Loud:** `reference_close` raises, which is rows 1 and 2 of the table. Nothing runs after it.
- **Silent, and worse:** `_stop_already_crossed` (`broker.py:1165-1184`) reads `body.get("c")`,
  finds nothing, and **fails open, returning False**. Crossed-stop detection is therefore
  permanently off against the fake. A run executes, produces a plausible record, and grades the
  wrong path with no error anywhere. That is why the F10 crossed-stop vehicle is listed NOT
  RUNNABLE rather than simply not yet run: running it today would have produced a confident
  result about a branch that never executed.

This is invisible in a normal `dnse_fake` run because `FakeVenueBroker` overrides both
`download_ohlcv` and `watch_ohlcv`, so the array-parsing paths are bypassed. It is exactly the
class of defect the suite exists to surface: the fake was only ever exercised through the one
door, and the other door was wrong.

## The OCO result, which is what the fake uniquely buys us

Shape A, stop-favoured (`slPct=0.05`, `tpPct=0.5`). The umbrella is `Activated` from birth with
exactly one normal-book child, and the stop leg then **amends that child in place**:

```
 11 d00000011a78dpg  New
 12 101159           New
 13 d00000011a78dpg  Activated
 14 101159           PendingReplace
 15 101159           New
 16 101159           Filled
```

One id, `New → PendingReplace → New → Filled`, no sibling spawned and nothing cancelled. That is
the measured venue model reproduced offline for the first time.

Shape B, TP-favoured (`tpPct=0.05`, `slPct=0.5`) is the discriminating control: the same child
goes `New → Filled` with **no** `PendingReplace`. So the amend fires on the stop side only, and
the pair proves the fake is modelling the asymmetry rather than emitting a `PendingReplace`
unconditionally.

**But the engine mislabels the leg, and then cannot let go of it.** Through the whole of shape A
the executed leg is labelled `tp`:

```
[BROKER] event FILLED id=101159 side=sell qty=1.0 filled=1.0 price=1992.7 pine='X' from='E' leg=tp
[BROKER] cancel -> wire | order=101159 book=NORMAL pine=X from_entry=E leg=TAKE_PROFIT
[BROKER] cancel -> wire | order=101159 book=NORMAL pine=X from_entry=E leg=TAKE_PROFIT
        ... repeating on an id the venue has already reported Filled
```

The child was amended to the stop price and filled there, and the engine still calls it the take
profit — then issues cancel after cancel against an order that is already `Filled`. This is the
#161/#164 family, reproduced offline and repeatable, where previously it needed a live session.

## The T10 dual blocker, measured rather than argued

Two engines against one account is the case the fake was supposed to give us cheaply. It cannot,
for two reasons that are both properties of the current design:

1. **Two `dnse_fake` engines are two separate venues.** Each broker builds its own `FakeVenue`
   and its own HTTP server on its own ephemeral port. Measured across today's runs: 33 distinct
   ports, one per run. Two engines would therefore never see each other's orders, and the
   isolation test would pass vacuously — the worst possible outcome for a test whose whole
   purpose is to detect cross-contamination.
2. **They share one bar store.** Every fake run resolves to `workdir/data/fakevenuebroker_VN30F1M_1.ohlcv`,
   and the broker parks that file at startup. The second launch parks the first run's file out
   from under it.

A vacuous pass is worse than a NOT RUNNABLE row, so this stays NOT RUNNABLE until a shared-venue
mode exists.

## What the second pass should fix, in order

1. **Serve `/price/ohlc` in the venue's real shape.** One change in `venue_http.py`; it unblocks
   rows 1 and 2 and restores crossed-stop detection for F10. Highest leverage by a distance, and
   it should come with a pin that drives a real reader (`_stop_already_crossed`) rather than
   asserting on the payload, because asserting on the payload is what failed to catch it.
2. **Derive the session phase from BAR time, not the wall clock.** Six NOT RUNNABLE rows are the
   scripts computing `session_phase()` from `datetime.now(ICT)` while the replayed day is a real
   session. The fake's own phase is fixed at construction and `fake_broker.py` never passes one,
   so today there is no way to pose a closed-hours question at all. This is the fix the leader
   anticipated and the table confirms it.
3. **A shared-venue mode** for two engines against one book, for T10.
4. **`startState = 0`** on the staged fill to cover F01 and F02.

## How each case was run

The `pyne run` vehicles, unchanged:

```bash
FAKE_VENUE_DAY=plugins/dnse/testing/fixtures/venue_day/DERIVED-FROM-1M_VN30F1M_2026-09-18.json.gz \
FAKE_VENUE_LIVE_BARS=<60..200> FAKE_VENUE_LIVE_PACE=<0.25|1.0> \
FAKE_VENUE_RECORD_FILE=plugins/dnse/testing/live_test/logs/suite_20260918/<case>.record.json \
.venv/bin/pyne run <vehicle>.py dnse_fake:VN30F1M@1 --broker
```

The staged probes need their window set past launch **plus warmup** — the committed values are
months in the past, so every stage would otherwise fire during warmup against the backtest
engine, which routes no orders. Launch plus 240 seconds worked for both. The configs were edited
for the run and restored afterwards; the pre-run copies are in `backup/deleteable/`.

The direct-client scripts (L0, T33, the T14/T15/T17 probes) hard-code the live config path with
no override. They were redirected by pre-seeding `DNSEBrokerConfig._ensured` with a
fake-pointing config before the script's own `ensure_config` call, from a harness in the session
scratchpad. **The live credentials file was never opened, never read and never rewritten** — its
sha256 is unchanged. That harness is a measurement tool, not proposed repo code; if these scripts
are to be run against the fake routinely they need a real `--config` flag instead.
